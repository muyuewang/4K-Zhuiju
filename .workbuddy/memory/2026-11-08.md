### 三条必须记住的坑

1. **content-type 完全不可信**
   - `newxfyun` 把 m3u8 标成 `image/png`
   - `JD4K` 把 m3u8 标成 `application/octet-stream`
   - 判定真实类型只能**读首字节**：`#EXTM3U` → HLS，`ftyp` → MP4
   - 也有 m3u8 地址根本不含 `.m3u8` 后缀（形如 `/m.php?data=...`）

2. **分片域名常与 playlist 域名不同**
   - NN蓝光分片在 `picasso-static.xiaohongshu.com`
   - JD4K 分片在 `nadou.inter.71edge.com`
   - 每片必须按**自身域名**生成 Referer，统一用 playlist 的 Referer 必 403

3. **`SH4K`（VIP4K）源是标准 HLS AES-128 加密**
   - `#EXT-X-KEY:METHOD=AES-128,URI=".../key/82109.key?auth_key=...",IV=0x7c2634dbc04a694b46197e47e2073371`
   - key 16 字节；密文长度是 16 的倍数；解密后首字节 `0x47`（TS 同步字节）
   - 去 PKCS7 padding 后才是干净明文
   - **不解密直接拼接 = 输出一堆密文，成品无法播放**（这是最初"下载成功但放不了"的根因）

## 下载器实现要点（lib/core/download.dart）

- `_downloadFile`：**必须带超时**（connect 15s / receive 30s），无超时的 Dio 在网络半挂时任务永久卡 running
- 服务器忽略 Range 回 200 时，旧 `.part` 内容作废，必须从头写
- 首块嗅探决定走 MP4 还是切 HLS（`_SwitchToHls` 内部信号）
- 进度 `_emit()` 必须节流 300ms，逐块发会把 UI 线程打满
- HLS 分片重试 **6 次 + 指数退避**（0.8→1.6→3.2→6.4→12.8s）；单片失败抛 `_RetryableError`，保留已下载分片整体续传（曾因单片失败丢掉 125 片）
- 拼接前检查全部分片是否齐全；成品用 `_isPlainTs` 校验，非法则改名 `.bad` 并报错，不留坏文件
- 下载前先调一次 `resolver` 刷新地址（时效 token 到下载时往往已过期）

## 收尾轮（release 验收 + 两处新缺陷）

### 缺陷 A：同一文件被登记两次（已修复）

`_adoptOrphanFiles` 原来用 **id** 去重，而索引里老任务的 id 是纯标题
（`兰香如故_第1集`），与收编时想用的 `兰香如故_第1集.mp4` 不相等，
于是同一个物理 MP4 被登记成两条，下载页出现重复行。

修复：
- 新增 `_hasPath(path)`：按 **filePath** 判断文件是否已被某个任务占用
- 新增 `_dedupeByPath()`：restore 后自愈历史脏数据，保留有 `sourceUrl`
  （可续传、信息更全）的那条，其余丢弃并打 `[DL] dedupe: dropped ...`
- 实机日志：`restored 3 tasks` → `dedupe: dropped duplicate task id=兰香如故_第1集.mp4`
- 结果：索引从 3 条降为 2 条干净记录，`.ts`（2.28GB）保留可见可删

### 缺陷 B：adb 点击坐标算错（必须记住的坑）

**截图尺寸 ≠ 设备真实分辨率**。`screencap` 出来是 **608×1080**，
而 `wm size` 是 **720×1280**，缩放比 1.1842。
按截图目测坐标点 `input tap` 会全部偏上偏左，落在「播放地址」文本区，
表现为「点了下载按钮但毫无反应」，极易误判成功能 broken。

正确做法：先 `adb shell wm size` 拿真实分辨率，再把截图坐标按比例换算；
或用 `uiautomator dump` 的 `bounds`（播放页因 Surface 层拿不到 idle 状态，
此时只能走截图 + 换算这条路）。

### 缺陷 C：release 包看不到 `[DL]` 日志

release 模式 `debugPrint` 被裁剪，`logcat -s flutter:*` 全空。
验证 release 包行为只能看**文件系统与界面**（`ls -la` 下载目录、`.tasks.json`、
`uiautomator dump` 的 content-desc），不要再等日志。

## 优化轮（10 项，全部实机验证）

### 下载核心（lib/core/download.dart）

1. **写盘节流**：`_emit()` 原来每次都全量序列化 + 落盘，141 片 HLS 就是 141 次
   写 JSON。改为 `_emit({persist})`：状态质变（开始/暂停/完成/失败/换源）
   立即落盘，纯进度走 1.5s 节流 + 1.6s 兜底定时器。
2. **HLS 分片并发**：原纯串行，94 片要十几分钟。改 3 路并发 worker
   （`Future.wait` + 共享 cursor），单片 6 次重试不变。
   **并发度必须是 3，不能是 4** —— 见下面「踩坑」。
3. **AES 解密零拷贝**：原每 16 字节 `sublist`+`fromList` 两次分配，
   20MB 分片 = 260 万次小对象。改复用单个 16 字节 `blockIn` 缓冲。
4. **HLS 拼接流式化**：原 `sink.add(await f.readAsBytes())` 把整片读进内存，
   2GB 剧集必 OOM。改 `openRead()` 分块（约 1MB）。
5. **`_save` 串行化（single-flight）**：并发后多个 worker 同时写同一个
   `.tasks.json.tmp` 再 rename，先完成的把 tmp 移走，后到的报
   `PathNotFoundException`（实测必现）。改 `_saving`/`_saveDirty` 串行队列。
6. **重复下载拦截**：已 done 的任务再点下载会从 0 重下并冲掉完整文件。
   改为直接复用；已 paused/failed 则复用原任务续传。

### UI 层

7. **播放页去掉逐帧整页重建**：`_onTick` 每帧 `setState((){})`，把「播放地址」
   SelectableText 和三个按钮一起重建。改为 `ValueListenableBuilder` 局部刷新
   （状态行时间、进度条、播放/暂停图标各订阅自己的）。
8. **新增本地播放页** `lib/pages/local_player_page.dart`：此前下载完成的文件
   **没有任何播放入口**，只能删除——几百 MB 等于白下。下载页每项加「播放」
   按钮（点整行也可），显示文件大小。
9. **下载页显示速度/ETA/重试状态**：`DownloadTask.speed` + `tickSpeed()`
   指数平滑 + `etaSeconds`；新增 `stage` 字段暴露「分片 N 第 M 次失败，重试中」，
   否则大分片连续超时时界面长时间不动，看起来像卡死。
10. **其它**：Api 网络类异常自动重试 3 次（业务错误不重试）；`PagedGrid` 加
    `AutomaticKeepAliveClientMixin`（切 Tab 不丢滚动位置、不重复请求）；
    `CachedNetworkImage` 加 `memCacheWidth`（列表 480 / 详情头图 720）。

### 踩坑（并发下载的代价，必须记住）

**并发 4 导致 93/94 卡死。** 根因：VIP4K 的末片不是普通 TS，而是
**302 跳到 `cmecloud.cn` 对象存储的 29.5MB 大分片**，单连接实测就要 **37 秒**。
开 4 路时互相抢带宽，双双超过 90s `receiveTimeout` → 6 次重试全灭 →
整体重试再来一轮，全程静默约 13 分钟。

修复三件套：
- `concurrency` 4 → **3**
- 分片 `receiveTimeout` 90s → **180s**
- 重试过程写入 `task.stage` 并在下载页显示

验证：修复前那轮最终仍成功生成了成品，续传后
`兰香如故_第2集.ts` = 1,260,950,692 字节，头 2MB 抽样
**11155 个 TS 包、同步率 100.0000%、首字节 0x47** —— 并发 + AES-128 解密正确。

`build_windows.dart:97` 抛 toolchain 错误。
