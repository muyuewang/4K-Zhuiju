### 关键技术结论（写进代码注释了）
1. **优子是 XML 站且两个出口互斥**：`ac=list` 按更新时间倒序但无封面无分集；
   `ac=videolist` 有全字段但按 id 升序（第一页全是 2022 老片）。
   `order=time`/`order=last`/`at=json` 全部被服务端忽略。
   解法：`ac=list` 拿最新 id → `ac=videolist&ids=a,b,c` 批量回查（243KB/20条）。
2. **XML 详情必须用 `ac=videolist&ids=`**，`ac=detail&ids=` 会**忽略 ids 返回随机 20 条**，
   详情页会打开成另一部不相干的片子。
3. **CDATA 必须剥**：`<dd>` 内是 `<![CDATA[集名$地址]]>`，不剥则 URL 带 `]]>` 尾巴 → 100% 404。
4. **金山 `/play/<token>` 是 1294B 的 Vue 空壳**（无 `var main`），但
   `…/play/<token>/index.m3u8` 实测 6/6 可播 → 新增 `derivePlayIndexUrl` 纯路径推导，
   省掉一次 1.3~1.9s 的无效抓取。**该规则对优子 `/share/` 不成立（实测 404）**，故做成开关。
5. 最电影（api.zuidapi.com）接口 5/5 通、片库 12.6 万，但 CDN `v15.zuidazym3u8.com`
   TCP 80/443 全 TimeoutError（连根路径都超时）→ 接口可用、片源不可播，**不接入**。

## 直播资产裁剪（2710 → 2694，删 16）

### 最重要的一条教训：抽样数据不能用来决定删除
我先用 450 个抽样得出「整体 88.9%、主播原创 86.7%、其他 68.3%」，
并据此建议给「主播原创」「其他」瘦身。**全量 2710 实测后全部推翻**：
整体 **98.5%**、主播原创 **99.7%（1454/1459）**、其他 83.0%。
按抽样结论删「主播原创」，等于删掉 1454 个能看的频道。
**结论：决定删除的动作必须全量实测，抽样只能用于发现线索。**

### 第二层的坑：HTTP 404 是状态，不是死亡
两轮复测都判死的 19 个里，14 个是 `live.ottiptv.cc/bilibili/<room_id>`。
直接问 B 站官方接口 `api.live.bilibili.com/room/v1/Room/get_info` 发现
**14 个房间全部存在**（12 未开播 + 2 轮播）。代理回 404 只是「主播此刻没开播」，
主播一开播同一 URL 立刻能播。资产是静态快照、URL 运行期才解析，
**保留 = 将来能看，删掉 = 永久失去**。

剩下 5 个转发链（yy/douyu/huya）隔时间复测，4 个一次就回 200 ——
`live.ottiptv.cc` 这个代理自身失败率不低。真正永久失效只有 1 个：
`咪咕直播 𝟛𝟜`（`gslbserv.itv.cmvideo.cn` 连 3 次 404）。

## v1.11.6：橘汁直播修复 + 直播多线路自动切换

### 橘汁「直播」为什么不能看：不是数据坏了，是播放分支走错

实测（`test/zhuiju_live_probe_test.dart`，走 App 真实代码路径）：
`category(25)` 返回 20 条频道分组，`detail` 的 path 是 `zb-cctv1` 这类逻辑名，
`playUrl` 换出来是真 M3U8，**抽查 6 条 5 条能播**。数据完全正常。

根因在 `detail_page.dart` 打开播放器时**没传 `isLive`**（直播页 `live_page.dart`
传了）。`isLive` 在播放器里控制四处行为，不传的后果：
把 26 个频道渲染成「选集 第1集～第26集」、用 m3u8 地址去请求「第0集」弹幕、
观看进度写进历史、**播完倒计时自动跳到下一个台**。

修法：不靠调用点传参（6 个入口都要改、容易漏），改成数据层打标。
`DramaVideo.isLive` 由 `ZhuijuSource._tagVideo` 设置，判据
`source == 'cctv' && path` 以 `zb-` 开头。**双向实测过才敢用**：
直播 114/114 命中 100%，电视剧 1947 条 / 电影 61 条 / 短剧 378 条全 0 误判
（见 `test/zhuiju_live_marker_probe_test.dart`）。误判的伤害远大于漏判——
正常剧集会丢选集、不能记进度、播完不自动下一集。

顺带修了两处播放器里对直播的漏判：
- `_saveHistory` 没排除直播 → 「最近观看」里出现「CCTV1直播 03:12」，
  点回去要么从头放、要么 seek 到一个早已滚出直播窗口的时间点
- `_onPlayTick` 没排除直播 → 部分 HLS 编码器会给直播上报 duration，
  position 走到 total 就被判成播完，3 秒后自动跳台

### 直播多线路：tvg-id 看起来是正解，实际是陷阱

第一直觉是用 m3u 的 `tvg-id` 聚合，**实测证明是错的**：`tvg-id="咪咕体育"`
底下是咪咕 1/19/30/4K-1 等 **38 个不同频道**，不是同一个台的 38 条线路。
tvg-id 在这里是「分类 id」而非「频道 id」，填充率也只有 7.1%。

改用「栏目 + 规范化台名」聚合（`tools/merge_live_lines.py`）：
去空白、剥 HD/4K/超清 后缀、统一 CCTV 的 1/-1/综合 写法。
**主播类整类跳过**——`YY用户` 69 条、`我是一颗小虎牙` 18 条那是 69 个不同主播，
聚成一个频道会让用户在几十个陌生人之间乱跳，比"不能切换"严重得多。

结果：2694 → 2676，12 组多线路（6 组 2 线 + 6 组 3 线），30 条备线路。
安全校验零疑似误并。

播放器侧：`_lineIdx` 记录当前线路，播放失败自动 +1 重试并提示
「线路 1 不可用，正在切到线路 2/3」；全部试完才报错且文案说清「N 条线路都试过了」。
线路的 **UA 必须跟着线路走**（`_playUa`）——同一个台的不同线路来自不同源站，
`101.35.240.114:88` 那条不带指定 UA 直接 404，用主线路 UA 播备线路会
出现「探活好的、切过去 404」这种极难排查的现象。
「重新连接」改为 `_reconnectLive()` 归零后重试全部，否则会在已确认坏掉的那条上打转。

## v1.11.6 交付：Windows 构建三个隐藏坑

`flutter build windows --release` 报 `Unable to find suitable Visual Studio toolchain`，
查下来是**三个独立问题叠在一起**，一个比一个隐蔽。

### 坑 1：Flutter 只认工作负载标记，不认编译器
`vswhere -requires Microsoft.VisualStudio.Workload.NativeDesktop` 和
`VC.CMake.Project` 都返回空，但 `VC.Tools.x86.x64` **命中**——VS 2022 Community
机器上 VC 编译器是装着的，只是缺那两个标记。`flutter_tools/lib/src/windows/
visual_studio.dart` 里 `_requiredWorkloads` 只查标记，查不到就 `cmakePath == null`
直接 `throwToolExit`。**编译能力本身完全正常**，所以绕过检测直接调 CMake 是正路，
不必重装 VS。

### 坑 2：环境变量大小写冲突把 MSBuild 打崩（真根因）
手动 `cmake --build` 才暴露：
```
error MSB6001: "CL.exe"的命令行开关无效。
System.ArgumentException: 已添加项。字典中的关键字:"HTTPS_PROXY"所添加的关键字:"https_proxy"
```
`HTTP_PROXY`/`http_proxy`、`HTTPS_PROXY`/`https_proxy` 四组同时存在，MSBuild 内部
用**大小写不敏感**的 Hashtable 装环境变量，插入即抛异常。清掉全部代理变量后通过。
（注意：报错信息指向 `CL.exe` 命令行，极易误判成编译选项问题。）

### 坑 3：`--target INSTALL` 拿到未展开的生成器表达式
`CMakeCache.txt` 里 `CMAKE_INSTALL_PREFIX:PATH=$<TARGET_FILE_DIR:zhuiju>`，
走 `cmake --build --config Release --target INSTALL` 时这个表达式不展开，
`install(CODE)` 里 `file COPY` 到该路径报 `Invalid argument`。
解法：`cmake --install build/windows/x64 --config Release --prefix <绝对路径>`。

### 坑 4：`flutter_assemble` 被判定 up-to-date 而跳过
`windows/flutter/CMakeLists.txt` 里 `add_custom_target(flutter_assemble DEPENDS
${FLUTTER_LIBRARY} ...)`，产物（`flutter_windows.dll` 等）已存在时 MSBuild 认为
无需执行，**Dart AOT 与资产打包就不会重跑**。
正确判断产物新旧的方法：不能只看 `zhuiju.exe` 时间戳（它只反映链接时刻），
要看 `build/windows/app.so` 和 `build/windows/x64/runner/Release/data/flutter_assets/`。

### 验证 AOT 里确实有新代码
`app.so` 里 Dart 字符串是 **UTF-16LE**，用 `grep -a` 按 UTF-8 搜会全部返回 0，
容易误判成「产物没更新」。正确做法：`d.count('正在切到线路'.encode('utf-16-le'))`。
实测 `正在切到线路` = 1、`条线路都试过了` = 1、`频道` = 6，证明新逻辑已进快照。
