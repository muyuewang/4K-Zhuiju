## 修复 jni 插件 /DELAYLOAD 失效（jvm.dll 硬依赖）

### 问题
`dartjni.dll` 把 `jvm.dll` 放进了**普通导入表**，没装 JDK 的机器一加载就失败。而该 dll 是 `jni_flutter`（由 `path_provider_android` / `shared_preferences_android` 传递引入）带来的 FFI 插件，Windows 上根本不该用到，却成了隐性地雷。

### 根因（上游 bug）
`jni/src/CMakeLists.txt` 里：
```cmake
if(WIN32)
  set_target_properties(${TARGET_NAME} PROPERTIES LINK_FLAGS "/DELAYLOAD:jvm.dll")
endif()
```
`${TARGET_NAME}` 在该文件中**从未定义**（真实 target 名是 `jni`），属性被设到空名字上，静默失效、无任何警告。

### 修复
在应用层 `code/flutter_app/windows/CMakeLists.txt` 的 `include(flutter/generated_plugins.cmake)` 之后补：
```cmake
if(WIN32 AND TARGET jni)
  target_link_options(jni PRIVATE "/DELAYLOAD:jvm.dll")
  target_link_libraries(jni delayimp)
endif()
```

**坑**：插件用的是 plain signature `target_link_libraries(jni ${JNI_LIBRARIES})`，CMake **不允许同一 target 混用 plain / keyword 两种签名**，写 `PRIVATE delayimp` 会报错。必须跟随 plain 写法。

### 验证（导入表对照）
| | 普通导入表 | 延迟加载段 |
|---|---|---|
| 修正前 | 含 `jvm.dll` | 无 delay load 段 |
| 修正后 | 仅 7 个系统 dll | 含 `jvm.dll` |

用 `dumpbin /IMPORTS` 时注意：要先定位 `Section contains the following delay load imports:` 行号，再按该行切分前后统计 dll，否则会把延迟加载的也算进普通导入。`/DEPENDENTS` 对延迟加载 dll 也会列出，**不能**用它判断是否硬依赖。

### 结论
不需要往目录塞 `jvm.dll` —— 单塞一个没用，它依赖 `java.base` 等模块，脱离 JDK 目录无法独立工作。延迟加载才是正解，装不装 JDK 都能跑。

## v1.11.1：移除金牌影院 + APK 回到单包

### 为什么移除（两个独立问题，都要记）

**问题 1 — 详情页「资源不存在」，是我的代码 bug**

`jplink_source.dart` 的 `_toDrama` 里写了 `sourceId: id`，而那个 `id` 是**影片 ID**（如 `59933`）。`Drama.sourceId` 的语义是**数据源标识**（应为 `'jplink'`）。

链条：首页拿 `d.sourceId`（=`'59933'`）传给 `DetailPage` → `SourceRegistry.byId('59933')` 匹配不到 → `byId` 兜底返回 `ZhuijuSource`（见 registry.dart:105-109）→ 拿 59933 去橘汁查 → 查不到 → 报错。

**这是个通用陷阱**：`SourceRegistry.byId` 在 id 不存在时**静默回退到默认源**，不抛错。所以任何源只要 `sourceId` 写错，表现都是「列表正常、点进去查错源」，极难一眼看出。加新源时务必核对 `sourceId` 是源标识而非条目 ID。

**问题 2 — 播放地址全部 403，源站侧问题**

接口返回的三档 m3u8 都带完整令牌：
```

```

**排查中踩的坑**：第一次打印 URL 时切片到 90 字符，把 `?t=...&whip=...&sign=...` 全截掉了，导致我一度误判成「接口给的地址是残缺的」。**打印 URL 用于判断可播性时不能截断**。

## v1.11.3：修复 PC 版 m3u8 慢 / 源站响应超时

用户报：同一地址（电影天堂《凡人修仙传》199 集）浏览器秒开、雷电模拟器也快，
唯独 Windows 版一直转圈最后报「源站响应超时」。

### 排查结论（逐条推翻过）
- 不是证书：服务器第 3 级是 ISRG CN=Root YR（2026 新根），openssl 报
  `unable to get local issuer certificate`，但 Dart 直连实测 200/97B 成功
  —— 各自根证书集合不同，openssl 的 verify 失败不代表 Dart/libmpv 会失败
- 不是代理、不是 DNS：直连与走代理均 200；5 个 A 记录全部 200，0.13~0.2s
- **真因：桌面端多绕了一层本地中转**。Android 走 ExoPlayer 直连、浏览器有
  自己的连接池，都不经过这层 —— 这就是「只有 PC 慢」的全部原因

### 两个根因
1. 每分片新建连接：`_fetchBytes`/`_fetchWithUrl`/`_relay` 三处各自
   `HttpClient()` + `finally close(force:true)`，等于每片重做 TCP+TLS 握手。
   一集 322 片 = 322 次握手。实测同批 4.24MB：串行+每片新建 20.3s(214KB/s)、
   并发+复用 10.6s(411KB/s)，而该流 3000k ≈ 375KB/s —— 低于码率必转圈
2. 零超时：`_relay` 里 `rq.close()` 与 `rp.forEach()` 都能无限挂起，
   最后靠 `initialize().timeout(30s)` 兜底报超时。源站本身也抖（单片 2.5s~22s）

### 修法（关键在第二层的取舍）
- **直连优先**：`wrap()` 起播前用 `findProxy=DIRECT` 的独立 client 探一次，
  能直连就把地址原样交给 libmpv（用它自己的并行预读），探不通才走中转。
  这是变快的根本原因 —— 不是把中转优化到极致，而是只让它服务真正需要它的源
- 中转内部：共享 `_upstream` 连接池（maxConnectionsPerHost=8, idleTimeout=15s）、
  分片 15s / 清单 10s 全链路超时、失败重试 1 次（`bodyStarted` 判安全性，
  已写响应体则绝不重试，否则播放器收到两份拼接数据导致花屏）、
  `_discardUpstream` 遇连接级错误丢池重建（`force:false` 不打断其它分片）

### 踩到的坑
- `Stream.timeout` ≠ `Future.timeout`：后者只是「不再等」，底层仍在读，
  数据继续灌进 res 把响应写坏
- 直连判定缓存键必须用 `scheme://host:port`，只用 host 会串味（同机不同端口）
- 三组代理内部回归（AES/302/多级展开）用本地服务模拟源站，天然可直连，
  直连优先生效后它们全会「测空气」→ 加 `HlsProxy.debugForceProxy` 开关
- exe 内嵌版本号来自 `windows/flutter/ephemeral/generated_config.cmake`，
  改 pubspec 后必须重新 configure + 重链 runner，否则 exe 还是旧版本
  （`flutter build windows` 在本机报缺 VS 工具链，改用 CMake 直接构建）
- 值类型：`_relay` 重试用例一度偶发失败，加日志才看出 `attempt 1 -> done=true`
  实际成功，是客户端侧时序问题，非逻辑缺陷

## v1.11.4：删除桌面端 m3u8 中转（推翻 v1.11.3）

### 为什么推翻
用户实测回「不行还是慢」，并指出「桌面端多绕了一层本地中转，Android 走
ExoPlayer 直连、浏览器有自己的连接池」。v1.11.3 做的是优化中转 + 直连优先，
方向错了：优化一个本不该存在的东西，天花板有限。

当时的核心误判：拿「能取到 m3u8 清单」当「直连够快」的证据。清单几十 KB，
分片是几百 KB × 322 个 —— **可达 ≠ 够快**。用户机器 Clash 常驻，浏览器和
雷电模拟器快恰恰因为走了代理，改成直连等于堵死唯一快的路。

### 关键实测（dart:ffi 直接问 libmpv，非推断）
- `mpv_set_option_string("http-proxy", …)` → 0 接受
- `mpv_set_option_string("http_proxy", …)` → -5 不认（那是环境变量名）
- `_putenv_s("http_proxy", 假代理)` 后 loadfile → 假代理收到 `CONNECT`
- 加 `no_proxy=该域名` → 假代理收 0 个请求
- mpv 已初始化后改环境变量**仍生效**

结论：libmpv 自己能走代理，中转层没有存在理由。`hls_proxy.dart`（约 920 行）
+ 5 组测试整体删除。

### no_proxy 语义（三轮实测，含重大缺陷）
| 写法 | 效果 |
|---|---|
| `127.0.0.1` / `localhost` / `::1` | 有效（精确项）|
| `probe.invalid` | 有效，且顺带匹配 `sub.probe.invalid` |
| `*.1.2.3` / `*.local` | 有效 —— 星号**只能做前缀** |
| `10.*` / `192.168.*` / `172.16.*` | **无效**（尾星不认）|
| `127.*` / `127.0.0.` | **无效** |
| CIDR `10.0.0.0/8` | **无效** |
| `<local>` | **无效** |

且按 **hostname 字符串**比对，不按解析后 IP（访问 localhost 写 127.0.0.1 无效）。
**IP 段无法用 no_proxy 表达**，一个 /8 或 /16 不存在等价写法。

修法：`MpvProxyEnv.bypass = 'localhost,127.0.0.1,::1,*.local'`，内网改由
Dart 侧判掉 —— `sync({targetHost})` 落在内网就整条代理不写。判定复用
`NetProxy.isBypassed`（私有提升为公开），全 App 只一份内网定义。

### 假测试教训
旧断言 `expect(bypass, contains('10.'))` 只验证三个字符存在，等于测空气 ——
正是它让 `10.*` 这个无效写法一路绿灯。改为断言不得出现尾星通配 / CIDR，
另加「内网目标必须直连」「公网目标不被误伤」两项。

### 顺带修掉的打包缺陷
- **`native_assets.json` 静默漏装**：CMake install 指向模板旧路径
  (`build/native_assets/windows/`)，新版 Flutter 产在
  `build/windows/x64/runner/Release/`。旧 `install(DIRECTORY)` 源目录不存在
  时不报错，只是什么都不做。踩了两次路径错：`CMAKE_BINARY_DIR` 和
  `$<TARGET_FILE_DIR>` 都指向 `build/win_cmake/`（CMake 自己的树），
  与 Flutter 的 `build/windows/...` 是两棵完全不同的目录。正解是
  `${PROJECT_BUILD_DIR}windows/x64/runner/${CMAKE_INSTALL_CONFIG_NAME}/`。
  改用 `install(CODE)` 在安装期判断，缺失时明确告警。
- **UA 补回**：中转删掉后 UA 落到 `Lavf/...`，带防盗链的源站会 403。

## Windows 硬解：实测确认「本来就在硬解」，无需改动（15:50）

用户提出「Windows 要做硬解」。按「改完用 `hwdec-current` 实测」的思路先做只读验证，
结果推翻了「Windows 在软解」这个前提。

### 三个容易踩的认知坑（都已实测钉死）

1. **裸 libmpv 默认 `hwdec=no`，但不等于 App 在软解。**
   `tool/probe_mpv_hwdec.dart` 直接 `mpv_create` + `mpv_initialize` 读到的确实是 `no`。
   然而 App 不走裸调用：`media_kit_video` 的 `NativeVideoController.create` 会显式写
   `hwdec: configuration.hwdec ?? 'auto'`，而 `video_player_media_kit` 内部是
   `Player()` + `VideoController(player)` 无参构造 → **App 拿到的是 `auto`**。
   拿裸默认值去推断 App 状态，结论会正好反。

2. **`MPV_HOME` + `mpv.conf` 注入无效。** 写 `hwdec=auto-safe` 后读回仍是 `no`，
   `cache-secs` 也没变 —— libmpv 默认 `config=no`，压根不加载 `mpv.conf`。
   这条路彻底否掉，别再试。

3. **`mpv_set_option_string("hwdec")` 在 init 前有效**（rc=0，读回生效）。
   这是唯一确认可用的程序化注入点。

### 实测数据（`tool/probe_hwdec_runtime.dart`，真起播读运行时属性）

| 配置 | H.264 HLS | HEVC 本地 mp4 |
|---|---|---|
| **`auto`（App 实际值）** | **`d3d11va-copy`** / nv12 | **`d3d11va-copy`** / nv12 |
| `no`（对照） | `no` / yuv420p | `no` / yuv420p |
| 显式 `d3d11va` | **`no`** / yuv420p ❗ | **`no`** / yuv420p ❗ |
| `auto-safe` | `d3d11va-copy` / nv12 | `d3d11va-copy` / nv12 |

**两条反直觉结论：**
- App 现在就是硬解，H.264 与 HEVC **都**落到 `d3d11va-copy`。不需要「打开」。
- **显式钉死 `hwdec=d3d11va` 反而退回软解**（`hwdec-current=no`）。别手动指定 API，
  交给 `auto` 让它自己协商。这一点如果没实测、凭「写死更稳」的直觉去改，会直接把硬解改坏。

### 探针自身的两个坑
- `mpv_set_option_string` 是**三参数**（ctx,name,data），和 `mpv_command_string`
  的两参数签名不同，共用一个 typedef 会编译期报 Too many positional arguments。
- 判断「是否已解码」不能用 `video-params/pixfmt` —— 正确属性名是
  **`video-params/pixelformat`**。名字写错会永远读到 NULL，表现成「一直没解出帧」，
  极易误判成硬解失败（本次先踩了这个坑，四组全空跑了 20s）。

### 残留未验证项
探针用 `vo=null`（无输出驱动，解出帧即丢），因为 `vo=libmpv` 依赖
`video_output.cc` 里的 ANGLE/OpenGL 上下文，控制台进程复刻不了。
所以已证明的是**解码器层会选 d3d11va**；「纹理上传是否零拷贝」属 ANGLE 那一层，
未在真机 App 内直接读到 `hwdec-current`。`-copy` 后缀即表示回拷到系统内存，
属正常硬解形态，不是软解。

### 结论
不改任何播放代码。FFmpeg 升级优先级按原判断继续压低。

## FFmpeg 升级完成：n6.0 → N-128766（mpv v0.36→v0.42，17:10）

**改 `pubspec.yaml` 的版本号不会升级 FFmpeg。** 版本由
`media_kit_libs_windows_video/windows/CMakeLists.txt` 里硬编码的归档决定：

1. `cp -r` 该包到 `code/flutter_app/packages/media_kit_libs_windows_video/`（30KB，纯脚本无二进制）
